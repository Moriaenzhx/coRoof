# 星桥软件：多角色经营演练

本案例是用户授权的完整本地模拟验收。所有公司、姓名、客户、制度、项目和结果均为合成数据；不接入飞书/GitLab，不投递真实邮件，不代表真实企业试点通过。真实业务流程通过公开 HTTP API 完成，不直接向业务表塞入最终状态。

## 公司与角色

星桥软件是一家 10 人的软件交付公司，同时推进两项客户工作。老板建立公司级项目并分配首项工作；各部门负责人在获得对应项目范围后继续拆分本部门事项。财务部门暂未录入任何数据，必须显示未知，不能计算虚构收入或健康度。

| 部门 | 角色与模拟姓名 | 测试责任 |
| --- | --- | --- |
| 企业 | 老板林澄（owner） | 企业全景、分工、制度发布、依据问答、决策/结果、经验偏好和关注授权 |
| 销售 | 负责人沈宁；员工许禾、赵远 | 需求范围、交接清单、续约材料；仅主管可管理本部门 |
| 研发 | 负责人陈屿；员工周然、唐悦 | 接口、界面、升级回归和取消旧脚本 |
| 交付 | 负责人顾岚；员工陆川、宋晴 | 客户资料、培训、验收记录和事项移交 |
| 财务 | 未录入成员与事项 | 无资料保持未知 |
| 外部对照企业 | 独立老板账号 | 猜测事项、知识和租户头均不能越权 |

每个身份使用独立会话，测试邮箱以 `example.com` 结尾。主企业和隔离对照企业都带“模拟”标记。真实身份认证与邮件投递不属于这轮验收。脚本报告给出本次账号、企业及资源 ID，不输出登录令牌、邀请令牌、Cookie 或 API Key。

## 可重复执行

先在隔离数据库检验同一个脚本：

```sh
cd backend
COROOF_TEST_DATABASE_URL='postgresql+psycopg:///coroof_v1_test_1103?host=/tmp' \
  .venv/bin/pytest tests/test_enterprise_scenario.py -q
```

测试使用随机 schema，结束仅删除本次测试 schema；关注执行使用原调度器和领域执行器。正式本地 HTTP 演练则经真实 API/Next.js 代理、PostgreSQL、Beat 和 Celery Worker，不手工写入运行或待办结果：

```sh
backend/.venv/bin/python scripts/enterprise_scenario.py \
  --base-url http://localhost:3000 \
  --label rehearsal-unique \
  --report .local/enterprise-rehearsal-unique.json
```

CLI 只接受回环地址和 development/test + mock 环境；拒绝覆盖已有报告。每轮使用新的 label 和报告文件。成功后保留可在网页查看的模拟企业；失败保留证据，并尝试暂停仅属于该轮的关注策略，不修改其他企业。运行报告中的 HTTP 延迟只是本机串行观察，不属于生产负载测试。

浏览器复核应以老板、交付主管和员工分别打开当前角色的工作台。老板先核对“需要留意的事项”、项目速览和实际团队动态，按需展开企业全景；主管核对本部门范围；员工从“工作清单”筛选或搜索本人事项，点击“汇报进展”或“需要支持”进入空白草稿。继续查看事项经过、制度、决策结果和经验待复核状态；至少验证一次明确确认后的页面提交与随后老板视图同步。正式商业发布仍需真实身份、外部服务、生产负载和真实团队试点。

真实开发模型采用相同的经营案例，在独立 PostgreSQL schema 中验证老板建议、主管范围、知识引用、私有资料隔离、员工草稿与本人确认。显式配置格式沿用 `scripts/model_acceptance.py`；不读取进程或应用内保存的密钥，每轮最多 19 次模型调用，无自动重试：

```sh
backend/.venv/bin/python scripts/enterprise_model_acceptance.py \
  --config-file .local/coding-plan-test.json \
  --database-url 'postgresql+psycopg:///coroof_v1_test_1103?host=/tmp' \
  --report .local/enterprise-model-unique.json
```
