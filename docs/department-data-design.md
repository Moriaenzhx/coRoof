# 统一空间、团队工作与经营数据设计

2026-11-06。状态：**统一空间模型与经营能力仍为设计稿；团队入口界面已更新**。设计企业、团队和跨团队项目空间，复用同一知识库、业务记录及 AI 入口。先行界面更新复用现有部门、工作、成员和项目接口，不新增空间实体、数据库或授权规则。交互原型中的示例必须标为合成数据。

现有实现以 [领域模型](domain-model.md)、[架构](architecture.md) 和 [Slice 02](slice02.md) 为准。下文“拟新增”均需另行实施、迁移和验收，不能当作当前产品能力。

### 已落地的团队入口

“团队”导航现进入团队空间目录：公司概览与同一企业知识库入口在上方，团队卡片显示实际获授权的待推进工作、明确支持需求和有效成员。整张卡片进入主页面内的团队工作台，默认看工作，成员按需切换；已结束工作和未归属团队人员折叠。参与项目仅从本团队可见事项的项目关联推导，不推断交接或依赖。

这只是现有部门的浏览与操作入口，不表示 Space、空间成员、专项财务权限或空间级 AI 范围已经上线。知识库入口仍显示全部本人有权查看的资料，不冒充团队资料筛选。空记录不推断健康，进入或切换团队不会触发模型请求。

## 1. 现状与目标

| 已有事实与能力 | 当前缺口 |
| --- | --- |
| 企业、部门、成员、项目、事项、负责人、截止时间、状态和业务事件 | 没有订单、客户经营台账、收款计划、实际到账、核销、验收或成本台账 |
| 明确支持需求、时间规则、老板安排、本人确认的成员反馈 | 事项完成不代表交付验收；支持需求不一定需要老板决策；没有已确认的跨部门交接关系 |
| 知识库、发布版本、权限、来源引用和失效处理 | 制度、合同文件和汇报文字不是结构化经营事实，不能据此生成收入、回款或利润 |
| 只读连接器框架、来源映射、Agent 有界读取与确认流程 | 外部经营系统未接入，部门财务权限、经营指标口径尚未建立 |
| 企业/部门工作范围、文档 ACL、持续关注的企业/部门/项目范围 | V1 尚无 Space、空间成员或统一空间查询契约；早期 Go 的 Resource/Relation/Context/Policy 仅是可参考概念，不是已实现空间服务 |

目标是让老板走进任一团队空间就能知道“这里在做什么、什么需要我、下一步由谁处理”，让主管和员工在同一结构里看到各自能处理的内容。空间组织工作、资料、业务数据和规则；AI 自动带入当前空间，用户不用每次重说部门。工作台复用已有项目、事项、事件和知识；经营数据通过明确的业务对象补齐，不把每条订单或每笔款项伪装成事项。

**完整结构不等于首批全部实施。** 首批围绕一个订单关联项目、一次交付确认、一笔收款计划与到账核对，以及一次明确交接跑通必要闭环；财务记录必须先有专项授权。成本、收入与利润属于后续逐项补齐的能力，不阻塞前面的工作协同。这里不建设完整 CRM、会计总账、税务申报、薪酬、人力资源或银行支付系统；已有专业系统仍可作为权威来源。

## 2. 同一套空间与知识入口

`Organization` 继续是不可跨越的企业租户边界。企业内部采用三种空间，首轮不增加任意层级嵌套：

| 空间 | 使用方式 | 与现有对象的关系 |
| --- | --- | --- |
| 企业空间 | 企业全景、公司公开规则、跨团队经营关注 | 每企业一个默认空间；企业全景仍在首页上方。企业空间的汇总先按权限过滤，不等于授权读取所有子空间内容 |
| 团队空间 | 销售、研发、交付、财务、法务等团队的工作、资料和数据 | 可以明确关联 Department，但空间成员和组织所属部门分别保存；老板无须把自己加入每个部门，员工也可以获邀参与多个空间 |
| 项目协作空间 | 跨团队围绕同一个客户、项目或目标协作 | 明确关联已有 Initiative 及参与人，使用同源记录与获准共享的交接包；参与项目不自动开放相关团队全部内容 |

“企业全景 → 团队节点”和“空间列表 → 团队空间”进入同一页面；原团队页从成员目录升级为空间入口，人员目录放到空间的低频管理入口。企业切换仍在设置中，与同一企业内的空间切换区分。返回全景保留位置。空间列表只列可进入的空间，不通过隐藏空间的名称、数量或最近活动泄露内容。

每个空间采用同一页头、同一组视图、同一资料列表和同一个底部提问框：

| 视图 | 默认内容 | 操作约束 |
| --- | --- | --- |
| 重点 | 一句话说明现状，最多三个可信数字，只突出一个最需要处理的事项 | 数字可下钻到同口径来源；其他进展按需展开，不叠加四套看板。无数据保持未知 |
| 工作 | 当前空间关联且本人获授权的项目、事项、明确交接与跟进 | 个人工作、部门工作和协作记录标明范围；只关联不改负责人或状态 |
| 资料 | 当前空间原有及明确共享进来的制度、文档、表单模板、附件 | 复用企业知识库的查阅、编写、导入、版本、分享与原文详情组件 |
| 数据 | 该空间业务模板下的结构化台账、表单记录和来源明确的报表 | 指标、金额、记录和动作分别受权限约束；没有相应台账时提示未接入，不伪造数字 |

空间规则、成员、持续关注与空间设置集中在一个低频管理入口；不把每种配置都放成常驻按钮。销售、研发、交付、财务、法务只是内容模板，视觉与操作不分成五套。模板由企业明确选择，不按空间名称或模型猜测；多职能空间先选择一个主模板，其他内容在资料与数据中查阅。

**企业知识库是同一资料系统的聚合视图，不是另一份知识库。** “知识库”入口默认查阅本人所有可见空间的已发布资料；进入某个空间的“资料”，只是加上空间范围。两处使用同一 Document ID、修订、原文件、分类、搜索、ACL 与分享命令，发布一次即可在获授权入口出现。资料分类表达“制度、合同、发票、表单、报表、客户资料”等内容类型，共享范围另作权限属性，不能继续用权限标签代替业务分类。未分类资料保留“未分类”，不让 AI 擅自确定分类或共享范围。

桌面可显示空间导航和紧凑视图切换，手机只保留当前空间名称、可展开的空间选择和同样的四个视图；不在手机并排摆空间目录与资料目录。字体、按钮、空状态、搜索、列表和详情复用一套组件，触控目标至少 44px。底部输入框标明“当前：财务空间”等简短上下文，小人保持右下悬浮，不另造空间专属聊天框或查询抽屉。

“最需要处理”优先呈现本人明确待确认的操作、已确认交接的待接收事项、到期需核对的记录及已提出的支持需求。若责任人未知，就写“尚未指定”；只有数据缺口时提示核对，不改写为老板审批、员工失职或客户违约。

## 3. 权限：先限定数据，再生成页面和回答

当前只有 `owner / manager / member`，没有 Space 或 `finance` 角色。空间为拟新增授权维度；下面是明确的新产品策略，不能只改前端菜单就视为已授权。经营台账和财务能力实施前默认关闭。

新建空间采用可预览的默认政策：当前企业 Owner 可创建、管理并进入本企业所有企业/团队空间，也可进入由企业管理的项目协作空间，无须逐个加入部门；空间内选择“空间共享”的普通资料和工作摘要按该政策向老板与明确的空间读者开放。创建者在创建/首次发布时看到实际读者范围。“管理空间”“读取内容”“处理业务”“共享/导出”“持续关注”是分离的动作能力；Owner 身份不能绕过个人私有、指定成员、未确认草稿或专项敏感字段限制。

普通成员进入团队空间需有效的空间成员关系或已确认的部门到空间映射；进入企业空间只开放企业共享内容。组织里的一个所属部门不等于只能参与一个空间，也不等于能看整个部门所有工作。空间成员授权可以自动包含常规空间共享资料的读取，但当前工作对象仍沿用对象权限；如需开放跨团队工作摘要，必须实现并确认具体对象或字段的分享授权，不能把全部空间成员映射成 Manager。

| 身份 | 现有工作数据范围 | 拟新增经营数据范围与操作 |
| --- | --- | --- |
| 老板 / Owner | 本企业事项；当前知识 ACL 无跨部门 Owner 特权，私人偏好和未确认草稿仍遵守各自权限 | 按新空间政策创建/进入/管理空间及常规共享内容；旧 ACL 不暗扩，经营汇总或敏感明细仍须新能力检查 |
| 部门主管 / Manager | 本部门或明确分配给本人的事项；成员目录仍按现有范围 | 通过明确授权管理本部门指定业务对象；不能因为管理项目而查看全部订单金额、成本、银行账户或其他部门台账 |
| 员工 / Member | 本人获分配事项与受限安排反馈；知识按文档 ACL | 工作台标为“与你相关”，只统计当前授权子集；可提交本人获授权记录的草稿，不自动开放全部门总量、成员目录或财务信息 |
| 财务专项授权成员 | 保持原有身份与工作范围 | 未来按能力分别授予收款计划读取、金额读取、到账登记、核销确认、成本或收入确认；授权包含企业、对象或部门范围、字段策略、期限和版本 |

财务专项授权不是把所有财务动作塞进一个新角色。读取金额、查看账户信息、导出和确认核销应能分别授权；敏感薪酬或账户明细不随普通成本汇总开放。谁可以授予及撤销这些能力，需要明确管理权限与审计，不允许成员自授权。

服务端执行“租户 → 可进入空间 → 对象或分享范围 → 动作能力 → 字段可见性”检查。有效权限取各层约束的交集，禁止把空间成员、模型给出的角色或 URL 当成授权证明。无金额权限显示“金额受限”，不传真实值到浏览器后再遮罩；对应总计、排序、搜索片段、导出、通知和 Agent 上下文也不能泄露隐藏字段。没有查看汇总的授权时，不通过企业总数反推被隐藏记录。

所有读取、提交、确认和历史详情重新检查当前权限。成员调岗、交接取消或专项授权撤销后，旧草稿不能继续确认，依赖旧权限的派生回答失效。跨部门关系不会自动复制权限，接收方只获得明确交接包允许的信息。

跨团队复用只采用三种明确方式：同源对象引用、向指定空间/成员分享明确字段或资料、为跨团队项目建立协作空间。引用只负责定位，不额外授权；真正共享由有权主体预览接收范围并确认。共享资料保留一个原件和版本，不在销售、法务、财务各复制一份合同。撤销共享会撤销该通道的访问与相关派生结果，独立有效的其他授权可继续存在；不能通过旧引用继续访问。跨企业共享不在本设计内。

移动资料只改变归属空间，不默认把 ACL 换成目的空间读者；移动前展示原读者、目的空间和实际访问变化，涉及放宽时须另行明确确认。新空间成员变动使继承型分享重新授权，指定成员分享不自动随部门调岗扩散。父子空间的视觉层级不隐式继承内容权限，私人草稿从不因空间共享而发布。

## 4. 数据字典与指标口径

### 共用字段

| 字段组 | 最小内容与约束 |
| --- | --- |
| 归属 | 企业、归属空间、对象类型与 ID、责任部门、责任成员；未知负责人保留为空。空间归属与业务责任分离，业务关联使用复合租户外键 |
| 来源 | 手工 / 导入 / 外部系统、来源记录 ID、源版本或内容指纹、导入批次、原始行号或证据引用、负责核对的人 |
| 时间 | 业务发生时间、所属期间 `period`、截止或计划时间、来源更新时间、录入与确认时间；时间点带时区，展示使用组织时区 |
| 金额 | 精确十进制金额、币种 `currency`、含税或不含税、金额用途与口径版本；不同币种不直接相加 |
| 状态 | 草稿 / 已确认 / 已撤销或更正，以及对象自身业务状态；确认者、版本和幂等请求标识 |
| 覆盖 | `complete / partial / unknown`、缺失项与已覆盖范围、统计时点；没有来源为 unknown，不等于零记录已核实 |
| 指标定义 | 名称、来源对象、期间与日期字段、过滤条件、计算方式、单位、币种、负责人、口径版本与更新时间 |

只显示当前范围内的事实。`complete` 仅表示指定来源、期间、字段和授权范围经核对完整，不代表掌握企业所有事实；不能从一次同步成功推断完整。真实 0 需要有完整口径与已核对的空结果。部分数据可以显示“已记录小计”，同时注明缺口，不能标为企业总额。

跨币种汇总只有在明确选择汇率来源、日期、版本与换算口径后才提供；否则分币种展示。期间变更、汇率或业务口径修改必须使相关汇总与分析重新计算，并保留原口径下的历史证据。

### 团队空间的默认业务字典

下表是团队空间的模板建议，业务台账均为拟新增。统计须同时限定当前空间、对象授权和明确的业务归属；共享进来的引用不重复计入自有业务金额。已有工作字段只能支持已记录事项统计，不能直接替代经营指标。

| 部门 | 默认最多三个核心指标 | 业务明细的最小字段 | 数据责任与边界 |
| --- | --- | --- | --- |
| 销售 | 本期生效合同额、待接收交接数、未来 7 天跟进数 | 客户标识、订单号、销售负责人、签约日期、生效日期、合同金额与币种、已确认变更、关联项目、交接及明确的跟进记录 | 销售登记、获授权人员确认；生效日期与签约日期分别保存，预计商机额不计入生效合同额 |
| 研发 | 当前参与项目数、未来 7 天到期事项、明确支持需求数 | 项目关联、研发事项、负责人、明确截止时间、生命周期、支持标记及事件来源、版本或交付物引用 | 从当前可见未完成事项按项目去重，不依赖默认项目状态；提交代码和任务数量不等于产品完成度 |
| 交付 | 当前已确认交付项目、待客户验收、明确支持需求 | 已确认交付登记或已接收交接、订单与项目关联、交付节点、交付物、客户验收要求、验收状态与依据、支持记录 | 交付与客户验收是明确记录；事项完成和内部验收不自动等于客户验收，未登记的节点不能推测 |
| 财务 | 本期已核对客户收款、未核销收款计划余额、待确认收款归属笔数 | 收款计划、到账日期与金额、币种、客户或订单归属、核对状态、核销目标及分配、来源凭证 | 由专项授权人员核对；收款计划不是已成立应收义务，未核销或归属待确认时先提示核对，不直接催款 |
| 法务 | 本人/团队待审事项、未来 7 天明确到期事项、待补材料事项 | 合同原件及版本、审阅请求、责任人、明确时间、审阅状态与已确认意见、关联订单/项目 | 首批复用授权工作与知识引用，完整审阅台账后续新增；没有真实审阅结果时不输出“合法合规”或“已获法务批准” |

时间基准统一为本次查询的统计时点 `T`。本期默认是组织时区下的本月，使用 `[期间开始, 期间结束)`，不纳入 `T` 之后尚未发生的事实；期间进度和统计时点一起显示。“当前”指标取截至 `T` 的有效状态，不只筛本月新增记录。“未来 7 天”按组织时区包括今天及随后 6 个日历日期，上界为今天 00:00 向后 7 个日历日的 00:00；实际筛选从 `T` 开始，不包含已逾期记录。例如 `T=11/06 10:30` 时显示 `11/06—11/12`，下钻明确范围为 `[11/06 10:30, 11/13 00:00)`。没有明确日期的不计入该窗口。历史期间查询须使用明确的历史统计时点，不能以今天的状态冒充过去快照。

| 指标 | 计算口径 |
| --- | --- |
| 本期生效合同额 | 汇总已确认、生效日期落在本期且截至 `T` 已生效的合同金额；已确认增减按各自生效日计入一次，撤销更正有明确冲回记录。签约在本月、生效在下月的合同不计入本月生效额；签约额是另一口径 |
| 待接收交接数 | 截至 `T` 已明确发送、尚未被指定接收方接收、未退回或撤销的交接记录，按交接 ID 去重；仅统计当前有权查看且与本部门相关的记录 |
| 未来 7 天跟进数 | 订单或交接中已确认、未完成且未取消、明确跟进时间位于未来 7 天窗口的跟进记录，按记录 ID 去重；不从合同到期日或普通备注推断跟进安排 |
| 当前参与项目数 | 当前部门范围内、当前用户可见且生命周期为 `planned / in_progress` 的事项，其非空项目 ID 去重数；不按 Initiative 的默认状态计数，无项目事项不硬造项目，部分可见时标为范围内参与项目 |
| 未来 7 天到期事项 | 同一权限和部门范围内，生命周期为 `planned / in_progress`、明确截止时间位于未来 7 天窗口的事项数；只统计已同步且有确定来源的日期 |
| 明确支持需求数 / 明确支持需求 | 当前范围内尚未完成或取消、原生 `needs_support=true` 的事项去重数；后续经营对象的支持记录另须明确确认并固定去重口径。外部支持字段未知、模型猜测或只有逾期均不等于支持需求 |
| 当前已确认交付项目 | 截至 `T` 有明确交付登记或已接收交接、当前交付记录仍有效且未结束的项目 ID 去重数；不是所有关联订单的项目，也不由任务完成率推导 |
| 待客户验收 | 截至 `T` 已提交并明确处于等待客户验收状态的交付节点数；按节点去重，内部验收不计，部分验收仅保留仍在等待客户确认的部分，退回整改另列待处理 |
| 本期已核对客户收款 | 实际到账日期在本期、截至 `T` 客户身份和客户收款性质均已核实的有效到账金额，按币种分别汇总；核对日期不改变到账所属期间。内部转账，以及客户身份或收款性质未核实的候选不计。客户及性质已核实、仅订单或期次待分配的款项可计入，但确认分配前不能抵减收款计划；退款单列，不默认为净回款 |
| 未核销收款计划余额 | 截至 `T` 已确认且有效的收款计划金额减去对该计划的有效核销分配，含尚未到期的计划，按币种汇总；不是到期未付金额或应收账款，不与待确认归属的到账直接相抵 |
| 待确认收款归属笔数 | 截至 `T` 有效入账记录中的两类待核对项：客户身份或收款性质尚未核实，标为“客户性质待核实”；客户及性质已核实、仅订单或期次未分配，标为“订单期次待分配”。两类均进入待归属列表，按到账记录 ID 去重，不按计划或核销拆分行计数；前者不计入客户收款，后者可同时计入已核对客户收款，均不能在未确认分配时抵减计划 |

**计划收款不等于已成立的应收义务。** 首轮不把计划余额命名为“应收账款”，也不把所有计划到期认作客户逾期欠款。完整结构预留独立的应收义务对象，包含成立依据、确认时间、金额、币种和到期条件，并预留明确区分“计划匹配”与“应收义务核销”的目标类型；接入专业财务来源并完成专项权限及口径验收后再启用应收义务核销，不能从计划自动生成。

**签约、生效、收入和回款是不同事实。** 收入记录由获授权者按企业明确的确认口径登记或从权威系统同步，不能仅凭签约、生效、开票、验收或到账自动生成。利润仅在对应期间、币种、收入和成本范围完整且口径经确认时计算，并写明是何种经营利润；成本缺失、分摊未知或口径不一致时只展示明细与缺口。分母为零时比率为不可计算，不填 0%。

## 5. 用业务对象连接部门，而不是复制四份数据

| 对象 | 关联与职责 | 关键约束 |
| --- | --- | --- |
| 订单（拟新增） | 客户、责任销售、签约、生效、变更及明确跟进记录；通过明确关联连接现有项目 | 签约与生效日期独立；支持一个订单对应多个项目、一个项目关联多个订单；金额归属与分摊须明确，跨项目不能重复计算订单金额 |
| 项目 / 事项（复用） | 组织具体工作；关联订单、交付节点或需跟进的业务记录 | 关联不改变现有工作权限或状态；不是凭关联就认定收入、依赖或完成 |
| 收款计划（拟新增） | 归属订单，可明确引用验收节点；保存金额、币种、计划日期与条件 | 与实际到账、应收义务分别保存；条件未满足、日期未知和明确到期分别表达；调整计划须确认并留历史，不能直接视为应收账款 |
| 应收义务（后续预留） | 来自专业财务来源或获授权确认流程，明确成立依据、客户、金额、币种、到期条件及关联计划 | 独立确认和权限，不从计划或已签约状态自动产生；来源、核销规则和验收未具备前不启用 |
| 到账与核销（拟新增） | 到账保存实际来源与经核对的客户归属；首批将到账与收款计划明确匹配，后续核销可引用已确认应收义务 | 分配目标类型、金额和币种必须明确；计划匹配不冒充会计应收核销。同一到账在两类目标间不得重复抵扣；并发校验可分配余额，预收、溢缴保留未分配余额 |
| 验收记录（拟新增） | 绑定项目和具体交付节点，引用交付物、验收者及证据 | 区分内部确认、客户或外部证据；部分通过不等于整个项目通过，模型不能代替验收者 |
| 成本记录（拟新增） | 发生期间、费用类别、金额、币种、来源和责任人；明确关联项目或部门 | 已发生、预算和预计成本分开；分摊规则与比例需确认，同一成本不能在部门与项目汇总中重复计入 |
| 收入记录（拟新增） | 确认期间、金额、币种、口径与来源，明确关联订单或项目 | 与合同金额及到账分别保存；更正收入不能篡改既有收款事实 |
| 跨部门交接（拟新增） | 引用订单、项目或节点，指明发送方、接收部门和成员、材料、期望动作与时间 | 一次交接有独立版本与状态；接收仅代表承担这次交接，不代表工作已完成 |

对象关系沿“订单 → 明确关联的项目 → 交付与验收”组织，收款计划连接订单及可选验收条件，到账通过明确分配连接计划；后续应收义务独立确认，核销目标类型不能混用。成本和收入通过明确归属连接项目或部门。每条关系都保留来源与确认者；不能只用同名客户、相同项目标题或文件名自动合并。

交接流程为：**发送方保存草稿 → 核对并发送 → 指定接收方确认接收或退回 → 接收后按约定跟进**。发送是显式业务命令，通知投递另有状态，不能把“已记录发送”写成“对方已收到通知”。接收前不偷偷改变事项负责人、创建对方任务或授权查看源对象全部字段。修改已发送的关键材料需要新版本和重新确认，取消要保留历史。

如果需要表达“验收通过后发起合同约定的下一期收款跟进”等依赖，必须记录具体前置对象、条件和依据，经获授权者确认后生效。**同属一个项目不能推导跨部门依赖、阻塞或排期。** 客户验收也不自动触发财务确认或外部付款。

空间中的业务内容与资料统一呈现，但保留正确的对象类型：

| 内容 | 在统一空间中的表达 | 不能混同的事实 |
| --- | --- | --- |
| 财务表单 | “资料”保存同一版本的模板和填报说明；“数据”保存有字段 Schema、校验、作者及状态的表单提交记录 | 上传 Excel 或 PDF 不等于已确认业务填报；表单提取只是待核对草稿 |
| 财务报表 | 报表文件使用统一文档版本；动态报表使用已授权台账、期间、口径版本与可下钻来源 | 报表文件中的数字不自动回写账本，不能把不完整资料生成的摘要当完整财报 |
| 发票与凭证 | 原文件属于同一知识文档或附件；发票业务记录保存经确认的号码、开票方、金额、日期、关联对象及来源版本 | 上传或识别发票不表示已验真、已付款、已抵扣，也不自动执行开票；OCR/验真服务另行接入验收 |
| 法务合同与制度 | 合同原件、模板、意见和制度采用统一资料组件，审阅事项显式关联该版本 | 文件存在不等于签署、生效或审批通过；法务意见须有来源、作者与状态 |
| 销售客户与项目资料 | 客户和订单采用结构化业务对象，客户文件、方案与项目文档用同源知识引用关联 | 客户名称相似不自动合并；项目参与不授予客户联系信息、合同金额或全部附件 |

拟新增 Space、SpaceMembership/Grant、SpaceResourceLink 与已确认 SpaceRuleRevision 等记录；具体命名以实施设计为准。每条资源仍有一个权威业务对象或 KnowledgeDocument，不把所有内容复制进一个无约束 JSON 容器。类型化关系必须具有租户复合外键；多目标链接要用可验证的关联表或约束，不能用任意字符串对象 ID 绕过数据库完整性。既有知识检索、版本、文件解析、事务命令和 LangGraph 持续复用。

## 6. 数据如何进入、如何更正

按“手工表单 → Excel 导入 → 业务系统只读同步”逐步接入。同一对象使用同一套校验与确认命令，不能因导入或来源于 Agent 而绕过业务约束。

1. **选择目标与来源。** 当前空间自动带入，用户只需选台账类型；切换空间会保留原草稿并解除旧提交绑定，不能自动把未完成导入写到新空间。上传文件进入隔离的待处理批次。Excel 是业务数据导入，不与知识库文档发布混为一谈。
2. **映射预览。** 用成熟 Excel 解析库读取内容，预览列名、示例、币种、期间、人员及对象映射。公式或宏不执行；未知日期、未映射成员、缺币种和不支持内容逐项标明。文件解析和行数有界。
3. **去重与校验。** 优先使用稳定来源 ID 与版本；同来源同版本重放无新增效果。无外部 ID 时只提出候选匹配，由人确认，不能靠标题或金额直接合并。校验租户关联、必填字段、日期、金额精度、余额和重复凭证。
4. **确认影响。** 清楚列出将新增、修订、跳过和冲突的记录、涉及的期间与金额。用户确认具体范围后才生效；无金额权限者不能借导入预览或错误信息读取金额，也不能确认财务记录。
5. **事务落库。** 按明确的原子批次或分批命令保存对象版本、追加 WorkEvent、更新投影并写审计；预检失败的行不得悄悄进入汇总。大批次若部分完成，显示已确认与失败行清单和批次状态，按幂等键可恢复，不能宣称全批成功。
6. **撤销与更正。** 未确认批次可以丢弃；已确认事实只能追加撤销、更正或反向分配记录并引用原事件。核销更正重新校验余额，关联合计重算，旧分析失效；不删除既有事件、静默覆盖金额或清空历史。

经营对象需要通过 Alembic 追加模型和租户复合外键。当前 WorkEvent 的目标约束不包含这些对象，实施时须显式扩展有外键的业务目标及“恰有一个目标”约束，不能塞进任意 JSON、伪造 WorkItem 或改动独立 Go 协议。新命令检查作者或所需确认能力、源版本、对象版本与幂等指纹；OpenAPI 仍是 DTO 唯一来源。

外部系统阶段先只读：连接范围、映射和启用由人确认，成熟 SDK、解析库、现有 Celery/Outbox 机制优先复用。同步保存来源版本与责任人，区分同步成功时间和事实发生时间；权威来源字段不允许本地直接覆盖，只能提交待核对更正。断连或撤权要停止刷新、标明覆盖缺口并按授权隐藏数据；不能把上次成功同步伪装成当前实时数据。外部写入、自动催款、自动付款不在本设计首轮实施范围。

## 7. Agent：证据 → 建议 → 确认 → 跟进

复用 LangChain 模型适配和 LangGraph 执行，不新造调度框架。当前 `RunInput` 只有事项与父查询绑定，没有类型明确的空间范围；绑定事项的运行还不能使用全局知识读取。实现空间上下文必须同时修改 DTO、服务端授权、工具查询和依赖失效，不能只在提示词里加“你现在在财务部”。

进入空间时，服务器解析当前身份及 `active_space_id`，返回可用视图、可读资源范围和已生效规则引用；底部输入自动显示当前空间。用户在财务空间问“有哪些需要我处理的”，默认只读取当前有权查看的财务工作、经营记录和相关资料；在项目协作空间问“现在卡在哪里”，默认读取该项目明确关联且获准共享的事实。进入空间可以读取现有关注项和规则提示，不自动调用 LLM，也不因此建立持续关注授权。

拟新增的查询上下文至少包含下列契约；客户端仅提交选择，服务器生成并校验有效范围：

| 上下文字段 | 行为 |
| --- | --- |
| `organization_id / actor_id` | 从已验证身份和当前有效成员读取，不信任客户端角色 |
| `active_space_id / scope_type / scope_version` | 企业空间、单空间或明确的多空间查询；校验空间状态、进入权限、查询模式与授权版本 |
| `resource_refs / source_versions` | 当前选中对象、同源关系及证据版本；对象引用不授予内容权限 |
| `effective_rule_revision_ids / policy_version` | 服务器计算适用于本次范围的已发布规则及版本，权限约束先于规则和提示词 |
| `parent_run_id / context_epoch` | 续聊只复用同企业、本人、有效会话及相容空间范围的已完成运行；切换空间隔离迟到响应与旧输入绑定 |

默认问题只在当前空间内查询；问句明确要求“结合销售和财务”“看全公司”时，可以把用户这次明确意图解析为多空间只读范围，服务端校验后在输入/回答中显示具体范围，不必让老板再逐项重复部门名。用户意图含糊或模型希望扩展范围时，只提供“同时查看相关空间”的明确选择，不暗中扩大。只能访问同企业的已授权记录，跨空间答案按来源标注空间，按对象 ID 去重；不知道的内容不能从其他空间数量或标题猜测。多空间查询授权不等于跨空间分享或长期关注授权。

空间规则分两类：已发布的制度/操作说明，以及有类型和校验的执行约束。企业规则提供共同基线，团队/项目只能在被允许的范围内补充；成员隐私、租户隔离、业务确认和专项权限不可被空间规则覆盖。经确认的企业强制规则高于空间规则，明确允许覆盖的默认项才可被空间细化；同级规则冲突或来源失效时提示待核对，不能让模型自行选择宽松规则。规则需有作者、适用范围、生效时间、版本和明确发布记录；修改影响依赖回答与待执行草稿。

资料、发票正文、合同条款和检索结果都作为业务内容，不作为系统指令。“忽略限制、读取其他空间、自动付款”等文件文字不会变成执行能力。普通知识文件不会因为被放进“规则”分类就自动获得策略权威，模型从材料提取的规则先是待确认建议。

- **证据：** 读取当前对象版本、同口径指标、来源时间、覆盖状态和权限允许字段；工作、合同、到账与制度分别标注。只读预填不调用，用户发送后才执行；持续关注仍须另行授予范围、期限和额度。
- **建议：** 先说明可确认的事实和缺口，再给至多一个优先动作及责任人。核销未完成时建议核对到账，不擅自认定客户欠款；无成本资料时说明不能判断利润。
- **确认：** 能力只能准备类型明确的草稿，由当前有权的作者或确认者核对；确认前重新检查来源、对象版本、金额和权限。草稿不能自行改负责人、派任务、发消息、发票、核销或付款。
- **跟进：** 以已确认交接、安排及实际反馈为依据。到期未反馈只表述“尚未记录结果”，不自动认定未工作、未收款或问题已解决；同一对象、同一原因去重，来源变化后再提醒。

跨空间问题只连接明确的业务关系。回答、摘要与引用继承最严格的来源字段权限，不能把老板可见的跨空间总结直接分享给无权查看来源的员工。新对象需要纳入现有证据版本及派生结果失效机制，未接入前不开放相应 Agent 能力。

切换空间时，未发送文字可作为原空间私有草稿保留，但新空间默认使用自己的输入与续聊上下文；显示“返回原空间继续”入口，不悄悄把原问题重新绑定。明确发起的任务继续在原空间范围执行，切页只收起浮层，不取消、不重跑、不带入新空间资料。完成后在“我的工作”按原空间记录，当前空间仅用不含敏感内容的状态提示；恢复结果与每步执行仍重查当前权限。切换企业或身份直接清空展示和输入绑定；旧任务结果不得进入新企业页面。空间归档、分享撤销、权限或规则版本变化时阻止后续读取/确认，清理相应缓存和派生内容。

### 小人的主动互动

小人是同一个 coRoof 伙伴，随当前空间切换关注范围。进入空间先读取当前范围内已存在、仍有效且未暂缓的关注项；最多轻提示一个与本人相关的重要事项，例如“这笔款已到账，归属还待核对”。点击后才展开事实与下一步，页面、焦点和导航不被抢占；无重要事项时安静待命，不每次问候、不自动弹整段分析。

提醒只来源于已确认支持需求、明确待确认操作、已确认交接或到期跟进、经过验证的关注结果；缺资料只说待核对，不能编造经营风险。去重至少包含企业、接收人、空间/共享业务对象、原因及事实版本；同一问题跨空间聚合只保留一个逻辑待办。已读、暂缓和忽略在同一接收人范围内生效，来源实质变化或约定时间到达后才允许重提；切换空间、刷新、动画重播和同步时间戳变化不重置去重。当前小人去重尚无完整空间维度，需要另行实现。

空间的持续分析沿用 WatchPolicy/WatchGrant、Celery/Beat 和有界执行图，明确授权目标、空间范围、期限、额度及接收人后才后台运行。企业统一模型预算仍是上限；无新事实不重复调用模型，授权过期/撤销立即停止后续步骤。进入空间只展示已有结果，与后台持续分析分别记账和测试。当前 Coding Plan 本机测试例外不允许后台 Watch，原型不得宣称现有测试凭据已能持续分析空间；真实模型与供应商用途边界仍须独立验收。外部消息、开票、付款等不随空间或持续关注开关开启。

## 8. 旧数据迁移与权限兼容

新增空间通过 Alembic 追加模型及租户约束，先将现有企业、部门、项目与空间建立可审阅映射；不会因为生成 SpaceMembership 就把所有成员升级为部门管理者。企业空间不替代 Organization，Go Runtime 与 `spec/` 保持独立。

现有知识 `private / department / organization / members` ACL 原样保留为兼容策略，旧 Document ID、修订、来源和 Agent 引用不变。尤其当前 Owner 并不自动读取其他部门的 `department` 文档；给旧文档挂上团队空间不能暗中让 Owner 或新空间成员读取。若企业希望采用新的“空间共享含老板”规则，需由有权主体明确选择资料或范围，预览新增读者并确认迁移；私有、指定成员和未发布内容不得被批量默认为空间共享。没有确认的旧内容继续用原 ACL。

旧知识库接口在没有空间参数时继续采用原授权语义；新接口的空间过滤只缩小候选范围，不能绕过原 ACL。新的空间共享策略以明确版本和命令启用，工作范围、金额权限与资料策略不混为一条继承规则。双入口始终调用同一知识命令与索引；不能为新空间复制文档、复制检索索引或让两套 API 各自产生不同发布版本。

发布、更改权限、移动、更正、归档或撤销分享要在同一受控命令中更新关系、追加适用业务事件/治理审计并标记依赖失效。查询、模型调用返回、草稿确认和外部文件读取结束都重查空间/来源/权限版本，旧响应不得覆盖新空间状态。被遮罩字段不得先进入模型，再指望模型不说。迁移有数据前后权限矩阵及对象数量对比，失败回滚不清空现有数据。

## 9. 实施顺序与验收门槛

每阶段先完成定向测试，通过后再进入下一阶段；以下均是待执行门槛，**没有宣称通过**。

| 阶段 | 可交付范围 | 进入下一阶段前的验证 |
| --- | --- | --- |
| 0. 结构与原型（本轮） | 企业/团队/协作空间、同一知识库、角色差异、空间上下文与业务模板 | 合成数据明显标记；老板进入空间即可判断范围；空间资料与知识库打开同一内容；跨团队来源可辨认；桌面/手机只有一个提问框；角色切换仅作演示，不视为真实授权 |
| 1. 空间与权限基础 | 空间实体、成员/授权、对象链接、老数据兼容映射；复用现有工作和知识 | 有数据迁移保留 ID/版本/原读者；Owner 可进新团队空间但读不到旧私有/指定资料；入空间不自动获金额或管理权限；租户复合 FK、调岗与撤权、移动和归档并发通过 PostgreSQL 验证 |
| 2. 统一空间 UI 与知识入口 | 重点/工作/资料/数据壳，知识库聚合与空间过滤共用组件/接口 | 同一文档发布一次两处更新；来源撤回两处及旧引用同时失效；计数、排序、搜索不泄露隐藏资料；列表全量统计不取第一页代替；移动端、键盘和返回位置通过 |
| 3. 空间上下文与主动伙伴 | Typed scope、规则版本、空间内问答、明确跨空间查询、小人轻提醒 | 不说部门名也绑定当前空间；切空间不串旧输入或迟到答案；已提交任务留在原范围；进入空间零模型调用；无变化无重复提醒/计费；规则注入不能扩大权限，后台授权与可用模型条件单独验收 |
| 4. 经营对象与基础录入 | 订单、项目关联、交付节点与验收；手工和 Excel 的映射、预览、确认、更正；法务/发票先用资料与明确类型记录关联 | 重复导入一次效果；跨租户关联拒绝；无映射不入账；任务完成不产生验收；上传发票不等于验真或付款；表单草稿无业务效果；切空间不得错投导入 |
| 5. 财务专项能力与台账 | 先落能力及字段策略，首批接收款计划、已核对客户到账和计划匹配；应收义务核销接入专业财务来源后另验，成本、收入及利润后续逐项实施 | 无金额权限时 API、汇总、导出和模型均无泄漏；PostgreSQL 并发分配不超额；计划不被当作应收义务；部分收款、待确认归属、撤销、更正、多币种和期间边界逐项测试；后续财务能力分别验收 |
| 6. 跨团队闭环 | 同源共享、项目协作空间、显式交接、接收/退回、安排与跟进 | 共享合同不复制金额、不开放整个财务空间；接收只看交接包；撤销分享使旧分析/草稿失效；发送不等于接收，未确认不分配工作，无关系不推断依赖 |
| 7. 系统接入与真实试点 | 明确选定的业务系统只读同步及小企业试点 | 分页、增量、幂等、断点恢复、权限撤销和来源陈旧验证；以真实用户验证理解成本；真实身份、部署、备份及恢复完成后才做生产发布判断 |

贯穿阶段的固定合成案例：同一订单本月签约 10 万元、下月生效，实际到账 4 万元、确认收入 3 万元，必须分别表达；本月生效合同额不计这份下月生效合同。客户身份或收款性质尚未核实时不计入客户收款；已核实为客户款、仅订单期次待分配时，可以同时计入已核对客户收款和待归属笔数，但不能抵减计划。尚未核销时不能宣称客户未付，计划余额也不能变成应收账款。订单拆为两个项目后合同总额不能翻倍；收入或成本不完整时不显示利润。每个数字都能下钻到同币种、同期间、同权限、同版本的组成记录。

每次业务代码实施仍运行仓库要求的 Python、Web 和现有 Go 检查；并发与迁移以 PostgreSQL 为验收依据，SQLite 不替代并发验收。本轮不调用模型、导入企业数据或改变线上授权。

前一版部门原型检查：文档链接与原型脚本语法通过；浏览器验证了三种角色、经营数据完整/部分/未接入、指标来源下钻、交接详情、建议与演示草稿。检查了 1024px 桌面、390px 与 320px 窄屏，所检查页面未发现横向溢出，员工交接按钮可用回车打开。这些是旧部门原型结果，不能视为新增空间、统一知识入口、服务端权限或生产验收；本次空间原型须按新场景另验，仍需真实用户试用评估理解成本。

本次空间原型检查：脚本语法通过；浏览器核对老板/销售员工两种视角、重点/工作/资料/数据视图、空间规则及财务报表入口。销售空间和知识库打开同一 `DOC-026 v2`；销售员工资料列表不出现财务报表和票据。显式选择跨团队范围并发送后显示范围与来源，切到财务时不携带销售输入或旧回答，重复进入已展示提醒的空间不再次弹出。1024px 桌面以及 390px、320px 手机宽度已检查，所检查的知识和跨团队/财务页面未见横向溢出。所有结果仅代表合成设计演示，不代表服务端权限、持久任务、模型回答质量或后台持续关注验收通过。

## 10. 开工前需定下的具体配置

- 首批企业/团队/项目空间如何映射现有组织和项目，谁可创建、管理、分享和加入；老板默认进入新空间的政策如何向发布者说明，哪些旧内容明确保持原 ACL。
- 首批演练选择哪个实际团队与一条业务链，谁负责销售、交付、到账核对及接收交接；不要求企业一次建全所有团队模板。
- 哪些企业规则属于强制约束、哪些默认项可由空间细化，发布者和生效流程是什么；持续关注的空间范围、目标、接收人、期限和模型额度分别是什么。
- 每类记录的权威来源、稳定编号与核对负责人；现有 Excel 的列、日期、币种、金额口径和覆盖期间是什么。
- 哪些人能查看金额、确认核销、导出或授予专项能力；老板需要哪些汇总，哪些账户或个人明细仍受限。
- 合同与收款计划的增减、验收条件和分摊规则；收入、成本与利润在后续采用何种明确口径，由谁确认完整。
- 第一批业务系统接哪一个、允许同步哪些对象与字段；未具备测试授权前先用明确标识的合成数据验收，不借原型默认值填入真实企业。
