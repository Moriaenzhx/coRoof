# Yuxi 对照后的五项体验改进

2026-11-05 用户授权：按会话执行、知识能力、企业协作闭环、老板交互减负、整体视觉五项依次实施并验收。企业全景仍位于首页最上方，小人位于右下，统一输入位于底部；老板和员工都使用自己的获授权范围。

## 1. 会话执行与恢复

参考 Yuxi 固定提交 `5c93360f0f013d78f070c5fd30320a009638a523` 的公开 Agent API：接收与执行分离、幂等回执、独立 worker、持久结果。没有配置 Yuxi 部署和授权凭据，其 uid/app/project 及知识撤权模型也不能直接替代本项目的企业、成员、原会话与来源版本。因此本轮采用现有 LangGraph/Celery 的兼容改进，不声称完成了远程 Yuxi 接入。

新增 `/agent/runs/submit` 明确接收只读指令，`AgentExecution` 持久保存投递和租约。浏览器仅轮询 GET；刷新后 `/active` 找回当前仍有权查看的任务。业务写入、草稿与持续关注授权保持原边界。取消、失权及未知模型调用均停止后续步骤；恢复须用户明确发起。迁移 0018 不回填历史任务。

开发门槛：PostgreSQL/Redis 98 项、相关 Web 93 项通过，包含独立 Worker 停止与恢复、重复投递、取消、租户隔离、来源失效、未知调用不重放、前端只读观察与迟到结果隔离。日志 `.local/agent-execution-postgres.log`、`.local/yuxi-stage1-web.log`。真实 MaaS 和 Yuxi 远程服务尚未验收。

后续补充门槛：最多三轮、总计 1,800 字节的上下文与逐层重新授权通过 PostgreSQL/Redis **100 项**回归；前端补充覆盖取消失败后仍能观察任务、刷新恢复，以及企业和成员范围切换时隔离旧响应。普通交互查询由用户明确提交，不因此取得持续关注授权。

## 2. 知识处理与质量

使用固定合成经营问答集比较旧检索与新排序，报告逐题排名、Recall、MRR、无命中及困难案例。复用 `rank-bm25` 的 BM25Plus，对 SQL 基础顺序前 500 个已授权、当前发布片段做词项重排，其余结果按原顺序接续，保留完整分页与总数；DOCX 复用 python-docx，保持段落、表格混排的正文顺序。Embedding、模型 Rerank 和 OCR 尚未接入，不将词项检索称为语义或向量检索，不下载本地模型代替用户指定的 MaaS。

开发门槛：PostgreSQL 知识回归 **73 项通过**，覆盖跨企业与私有资料候选过滤、撤权并发、准确引用、500 候选边界与完整尾段分页、同分稳定、DOCX 顺序及固定集质量；Ruff、格式和 mypy 通过。固定 12 篇合成经营资料、23 个问题中，21 题有参考文档、2 题无答案；前后使用同一题集，SHA256 一致。Recall@1 **83.33% → 88.10%**，Recall@3 **90.48% → 90.48%**，MRR@3 **88.10% → 90.48%**；无答案问题均未误命中，返回的原文引用全部校验通过，**0 次模型调用**。两道口语转述仍未命中，保留为未解决案例，没有调整参考答案来掩盖退化。

报告为 `.local/knowledge-retrieval-baseline.json`、`.local/knowledge-retrieval-quality.json`，日志为 `.local/knowledge-stage2-postgres.log`、`.local/knowledge-stage2-quality.log`；执行方法、指标口径与后续语义模型接入边界见 [知识库验收](knowledge.md#2026-11-05-词项检索与解析改进验收)。这是本地固定小型合成集的阶段门槛，不代表真实企业规模、通用语义问答或后续界面已验收。

## 3. 老板安排到员工反馈

员工在自己有权查看的事项中看到已确认安排，按现有草稿流程提交反馈；本人确认后关联原安排追加业务事件。老板可以查看实际反馈。未确认方案、私有分析上下文不对员工开放；反馈不自动证明安排完成，也不自动改变事项状态。

开发门槛：PostgreSQL 相关回归 **55 项**、最终定向回归 **12 项**通过，覆盖确认安排 → 获授权员工读取 → 反馈草稿无业务效果 → 本人确认一次 → 老板查看，以及跨企业、移交撤权、旧版本、幂等与非作者拒绝。SQLite 补充回归 **9 项通过、2 项 PostgreSQL 专属用例跳过**；PostgreSQL 对应覆盖和最终全量验收见下文。非空数据库迁移保留既有记录，旧反馈草稿不被补造安排关联。模型与事务边界见 [领域模型](domain-model.md)。

## 4. 降低操作成本

首页保留全景与少量需要处理的事；事项提供一个明确的主操作。员工进入汇报时先看到要处理的安排和输入，来源、技术说明及历史细节按需展开。模型、工具、连接及额度集中到设置，不向老板日常工作流铺开。

开发门槛：相关 Web **101 项通过**，覆盖老板与员工的单一主动作、细节默认折叠、键盘和输入法、无隐式发送，以及业务确认保留。打开页面或准备反馈不会代替本人确认。

## 5. 统一视觉与反馈

统一字号、间距、控件、层次与动效；减少嵌套边框卡片，提升内容可读性。全景保留柔和转动；底部输入与居中结果轻盈但清晰，手机触控目标充足，系统减弱动效有效。

浏览器验收通过：本机新版本在桌面、1024px 和 390px 宽度检查均无页面横向溢出；64px 折叠导航无按钮溢出，中屏部门网格无额外空区。手机回答浮层底边 663px、输入区顶边 677px，互不覆盖；桌面滚动到底后，页尾底边 611px、输入区顶边 647px，保留操作空间。系统减弱动效规则和暂停入口保留；未用脚本修改用户系统动效偏好。

使用现有合成账号核对老板、研发员工和交付员工：企业全景保持首页首位；员工首页只显示自己的事项，交付员工能看到既有已确认安排和“反馈安排”入口，汇报入口直接聚焦原文输入，AI 整理方式默认折叠。研发员工仅见企业共享与研发部门两份文档；查询切页后仍完成，刷新后的查询记录在“我的工作”保留。连续询问“企业知识库有哪些资料？”→“里面写了什么？”成功返回当前授权目录和原文，明确标注未调用模型；没有将老板查询记录带入员工视角。安排的确认与反馈写入闭环由阶段 3 的 PostgreSQL 和 Web 用例验收，本次浏览器未追加虚构业务进展。

浏览器中发现目录自然问法未命中快捷读取，补齐严格的知识库容器句式并通过 **37 项 PostgreSQL 回归**；审批、具体要求和风险问题不误路由，新增正反例及真实 API 权限/零模型调用断言。补丁静态检查通过并再次部署。截图位于 `.local/yuxi-owner-workspace.jpg`、`.local/yuxi-employee-workspace.jpg`、`.local/yuxi-employee-answer.jpg`、`.local/yuxi-mobile-answer.jpg`。

本机数据库已备份后升级到 0019；迁移前后企业、事项、业务事件、决策数量一致，API/Web/Worker/PostgreSQL/Redis 健康。原有真实模型配置未改动，测试公司预算占用仍为 43,066 Token；首个未匹配目录路由的问题被现有预算门槛拒绝，本轮没有提高额度，也没有将原文检索验收称为真实模型问答验收。
