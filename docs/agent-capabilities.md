# coRoof V1 Agent 能力与执行边界

日期：2026-11-03 设计基线；2026-11-04 更新：工作读取、知识检索与运行循环、AI 更新草稿、引用决策与本人确认已实现，并按用户要求接入 LangChain / LangGraph。经验、偏好和主动提醒仍是后续阶段计划。

## 产品与架构决定

coRoof 面向老板的经营目标，提供理解问题、查询事实、分析选项、准备行动和复盘经验的 Agent。企业知识库已接入；长期记忆继续保留在后续范围中。

V1 不接入 Skills，不加载或执行 SKILL.md、第三方技能包或模型生成的技能。能力由产品需求定义，开发人员以版本化代码和测试维护。业务能力表达“解决什么问题”，工具是服务器实现该能力的方法。

LLM 可以建议下一项业务能力及其业务参数，根据受控结果继续判断；它不能直接选择并执行任意底层工具、请求地址、SQL、脚本或外部 API，也不能授予权限。即使供应商使用 function/tool calling 格式，输出也只作为不可信提案，不接 SDK 的自动执行回调。

```text
用户目标 + 已验证的会话身份
  -> Harness 提供当前任务可申请的业务能力
  -> LLM 输出 CapabilityProposal（能力 ID、业务参数、相关证据）
  -> 服务端校验能力、参数、当前权限、对象范围、额度和有效性
  -> 服务端固定映射到已注册的工具 / 领域服务
  -> 只读操作执行；业务写入准备可审阅的草稿
  -> 用户明确确认后重新授权、核对版本并执行写入
  -> 返回结构化结果、依据、执行状态，供模型继续判断或结束
```

Harness、授权校验和工具执行首先作为现有 Python 模块化单体的内部模块，不新建微服务，不接通早期 Go Runtime，不修改 spec/ 共享协议。

## 老板需求与能力目录

以下 ID 是业务设计目录，不等同于全部已暴露给模型的工具。读取目录四项已上线；更新草稿通过显式 update_draft 任务接入，决策准备、确认与结果仍经独立业务 API，由 LangGraph 连接等待和执行。其他项的“已有基础”只表示领域服务可复用，不能视作 Agent 已实现。

| 能力 ID              | 老板的需求 / 痛点            | 交付内容                                    | 服务端可使用的工具或服务             | 范围、写入与当前基础                                                                            |
| -------------------- | ---------------------------- | ------------------------------------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------- |
| company.overview     | 不知道企业现在发生了什么     | 公司摘要、记录覆盖率、更新时间、信息缺口    | 授权范围内的组织、工作、信号聚合     | Owner 企业范围；Manager/Member 仅各自可见范围，不能输出企业全量结论；已有基础                   |
| attention.explain    | 不知道哪些事情需要自己关注   | 逾期、支持需求、节点阻塞、数据陈旧及依据    | 工作查询、信号查询、证据读取         | 只读并复用事项权限；优先级说明区分规则与模型判断；已有基础                                      |
| work.investigate     | 只看到表面状态，不清楚经过   | 事件时间线、已知事实、待核实原因和缺失信息  | 事项、事件、证据查询                 | 只读；无记录不归因、不把推测写成事实；已有基础                                                  |
| people.context       | 不清楚谁负责、协作找谁       | 职责、归属部门、已分配事项及相关记录        | 成员、部门、事项查询                 | Owner 企业成员，Manager 本部门及本人，Member 本人；已有基础；事项数量不代表能力、工时或空闲程度 |
| coordination.prepare | 有阻塞，但不知道怎样协调     | 资源需求、协作对象、处理步骤的待确认方案    | 上述只读服务、方案草稿构建           | Owner/Manager 可在管理范围准备；不自动分配、不发送消息；有查询基础，执行绑定待补                |
| decision.prepare     | 多个方案难比较、缺少决策依据 | 选项、代价、假设、依据及待确认决策          | 本人分析、证据、决策准备服务         | 仅 Owner；准备草案与确认分开，确认绑定具体方案和版本；已有 Slice 02 基础                        |
| decision.follow_up   | 做过决定后缺少结果回看       | 决策背景、跟进安排、实际结果及未记录的结果  | 决策/结果读取、结果草稿与确认服务    | 仅 Owner；实际结果由人明确提交，模型不能自行判断成功；已有记录基础，主动提醒待实现              |
| knowledge.search     | 资料分散、反复询问同样的问题 | 带来源、版本、时间和适用范围的原文回答      | 获授权的文档检索、片段读取           | 已实现；只检索当前可读的已发布版本，逐字校验引用，权限与来源变化使旧结果失效                      |
| experience.reference | 相似问题反复踩坑             | 相似决策、实际结果、适用条件与差异          | 决策历史检索、经验检索               | V1 仅 Owner；已有决策与结果，经验提炼和检索尚未实现                                             |
| preference.manage    | 每次都要解释经营重点和习惯   | 偏好候选、来源、确认/修改/撤销/删除         | 本人偏好读取、候选保存、确认管理     | 仅对应 Owner 管理本人偏好；明确确认后生效；尚未实现                                             |
| work.update_draft    | 老板掌握不到一线的实际变化   | 员工原文和可编辑的结构化更新草稿            | 草稿生成/编辑、作者确认、事件服务    | 只能处理当前获授权事项；只有草稿作者可确认，Owner 也不能代确认他人的草稿；已有基础              |
| coverage.explain     | 不知道系统掌握的信息是否完整 | 本次覆盖范围、未接入来源、陈旧/同步失败提示 | 当前记录覆盖统计，后续连接器同步状态 | 按对象和来源授权；当前有覆盖提示，外部同步尚未实现                                              |

财务、回款、绩效等缺乏业务模型、授权和来源的请求，返回明确的能力或数据缺口。老板优先体现在关注目标、信息排序、决策支持和本人偏好；不扩大员工或其他企业数据的访问范围。

## 能力契约

每个能力在接入运行循环前必须明确下列内容，由服务端注册表维护。需要新增公开 DTO 时以 Pydantic/OpenAPI 为源生成前端类型，不在本文件维护第二套可执行 Schema。

| 字段组       | 需要定义的内容                                                  |
| ------------ | --------------------------------------------------------------- |
| 业务语义     | 稳定 ID、版本、解决的需求、允许和不支持的场景                   |
| 输入与输出   | 严格类型、必填字段、长度/分页限制、输出 Schema 版本、缺数据表达 |
| 授权         | 角色、租户、对象和字段范围；知识/记忆的可见性与用途             |
| 执行映射     | 服务端固定的处理函数和工具允许列表；输入不能覆盖该映射          |
| 副作用       | 只读、草稿、确认后业务写入；原始来源权威性和外部目的地          |
| 确认与一致性 | 确认主体、待确认参数、有效期、对象版本、幂等和重试规则          |
| 运行限制     | 最大步骤、模型和工具超时、返回大小、费用/调用额度、取消与恢复   |
| 结果与审计   | 证据 ID、来源时间、覆盖范围、执行状态、失败码、脱敏审计信息     |

提案不接受模型提供的 role、actor、organization、approved、credential、工具地址或执行代码。身份和租户来自可信会话，目标对象 ID 和查询条件仍必须验证。模型不能决定自己的权限、费用上限或确认状态。

## 执行与确认规则

1. 能力目录按当前任务和权限裁剪；每次真实执行仍重新授权。隐藏工具名称不能代替权限校验。
2. 校验成员是否有效、当前角色、租户、事项/部门/文档范围与来源权限。后台任务使用单独的限时授权上下文，不自动继承无限期 Owner 权限。
3. 对未知能力、额外字段、越权对象和未实现依赖默认拒绝。校验成功后，执行器才选择固定工具，并只传必要数据。
4. 只读查询在授权和预算内可连续执行，不要求老板逐次点击。结果返回模型前过滤敏感字段并检查当前可见性；会话历史、摘要和缓存也不能绕过权限撤销。
5. 生成方案或草稿不是执行。写入确认绑定主体、企业、能力版本、目标、完整参数、证据/对象版本和有效期；模型的“用户已同意”或 approved=true 不是确认凭据。参数变化后重新展示并确认。
6. 确认后再次检查权限、来源权威性和新鲜度；业务服务用事务、版本检查、幂等和审计执行。用户确认不覆盖服务端拒绝。写入结果未知时先核对持久化结果，不盲目重试。
7. 只有执行器确认成功的结果才能被描述为“已记录/已完成操作”。未支持、拒绝、等待确认、过期、取消和失败必须分别表达。
8. 保留任务与工具执行记录以支持恢复；恢复时重查授权、确认有效期和执行状态。模型调用不持有长时间数据库锁。
9. 循环设步骤、时间和费用上限；重复调用无新信息时结束或请求必要信息。记录模型/提示/能力/策略版本，不保存模型隐藏推理或无关敏感全文。
10. V1 不提供任意 SQL、Shell、HTTP 或外部写入工具；外部文本、检索片段与工具输出属于资料，不能改变系统规则或能力注册表。服务密钥只由对应执行组件使用。

当前服务中已有部分幂等与版本机制，但并非所有创建接口都具备 Agent 重试需要的契约。例如创建 WorkItem 当前使用新对象 ID 生成事件去重标识，不能直接作为可任意重试的 Agent 写工具。每个写能力启用前必须单独验收，不能因已有 HTTP API 就自动暴露。

## 知识、记忆和成长

知识库、经验与偏好只通过受控业务能力访问。检索前限制企业和文档权限，返回前校验来源可见性；模型上下文不装入未获授权的材料。来源更新、删除和权限撤销需要影响检索索引、缓存和派生记忆。

已授权业务事实可以随来源更新。经验提炼先形成带依据和适用条件的候选；已确认决策的实际结果用于核验，模型的复盘文本不是新的业务事实。老板偏好需要本人明确确认，支持纠正、撤销和删除。员工上下文只包含获授权的工作信息，不从零散文字固化人格、能力或绩效评价。

成长通过更完整的事实、经核验的经验、已确认偏好以及评估后的产品能力改进实现。模型可以提出改进建议，但不能自行注册新能力、放宽权限或发布执行逻辑；本阶段不引入 Skills 或自动模型训练。

## 下一轮实施顺序

前置步骤：按 [统一模型层设计](model-layer.md) 抽离 ModelGateway、模型配置和供应商适配器，先迁移现有依据问答并验收百炼通用 API 的 Qwen 配置。下列 Agent 提案复用该入口；模型层不执行工具，也不决定业务权限。Coding Plan 凭据不接入 coRoof 后端。

1. 建立能力注册表、提案校验、授权执行器与可持久化的任务循环。先接 company.overview、attention.explain、work.investigate、coverage.explain 四项读取能力；具体是否可用由服务器按当前身份和数据范围决定。
2. 接入 decision.prepare 与 work.update_draft 的草稿路径，再以明确确认接入已验收的业务写入。没有确认时仅展示建议或草稿。
3. 按既有后续 Slice 边界接入知识检索、经验和偏好，以及只读外部来源；每项依赖就绪后单独启用。未实现能力不进入可执行目录。
4. 在上述契约稳定后增加后台主动关注、失败恢复和评估回归。正式试点仍先满足真实身份、邀请投递和部署控制。

## 启用前验收

- 在两家企业、Owner/Manager/Member 身份下验证目录、执行、证据、聚合、会话和恢复的权限一致性。
- 伪造身份、approved 字段、能力 ID、工具 URL、SQL 或脚本不产生执行；知识片段中的调用指令不改变权限。
- 模型在获授权读取之间能根据真实返回结果选择下一能力；额度用尽、取消或重复无进展时正确停止。
- 等待期间撤销权限、移交事项、修改参数或对象版本后，旧确认无法执行；老板不能代确认员工草稿。
- 重复确认、任务重试、进程恢复只产生一次业务效果；结果未知不会被标成成功。
- 缺证据、来源冲突或能力未实现时明确表达；测试模型失败与规则降级，不把规则结果呈现成真实 Agent 分析。
- 知识/记忆启用时验证来源引用、当前权限、删除/撤销传播及错误经验纠正。

本文件定义的是验收要求，不是通过记录。当前运行系统和已有测试结果仍以 [Slice 02](slice02.md) 为准。

## 持续关注增补（2026-11-04）

用户明确要求 Agent 在后台持续运行，主动规划团队事务、推进项目、发现有依据的问题并交给老板决定。详细契约与验收见 [持续 Agent 设计](continuous-agent.md)。复用现有 LangGraph 图、确认服务和 LangChain 模型层；业务事件/定时触发由 Celery 与持久化 outbox 调度。支持资料不足时提出待核实问题，但不编造目标、能力、依赖、风险或实际结果。阶段 4–7 提供来源、知识、偏好与运行控制，阶段 8 实现持续关注策略和老板待办。
